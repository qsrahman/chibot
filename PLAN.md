# chibot — Product Requirements & Plan

A local, single-user, ChatGPT-style web chatbot built directly on the
[OpenAI Responses API](https://developers.openai.com/api/docs/guides/responses-vs-chat-completions)
via the official `openai` Node SDK. It works with OpenAI and with any
OpenAI-compatible server that implements the Responses API (e.g. Ollama,
LM Studio).

## 1. Goals

- A chat experience that feels like ChatGPT: streaming answers, Markdown and
  code rendering, a conversation sidebar, stop/regenerate/edit with message
  versions, attachments and tools.
- Built **incrementally**: every phase ships working code, tests, docs and a
  commit.
- A codebase that is simple to read and easy to extend: a handful of
  well-named classes, constructor-injected dependencies, no speculative
  abstractions.
- Lean on the platform: Node built-ins (`node:sqlite`, `process.loadEnvFile`,
  `crypto.randomUUID`) and the `openai` SDK's own types instead of hand-rolled
  equivalents.

## 2. Non-goals

- Multi-user support, accounts or authentication (it's a local, single-user app).
- Hosted deployment (serverless platforms are not a target).
- OpenAI-hosted tools (`web_search`, `file_search`, `image_generation`,
  `code_interpreter`, remote MCP). Every tool is our own function tool.
- Providers that only implement Chat Completions (`/v1/chat/completions`).
- Several chat providers at once. One chat provider is configured in `.env`;
  switching means editing it and restarting.
- A git remote or CI. Commits stay local; checks run before each commit.
- Dollar cost estimates. The SDK has no pricing data and a hand-kept price
  table would go stale, so usage is shown in tokens only.
- Read-aloud (text-to-speech), realtime voice conversations, mobile apps.
  Dictation is in scope (Phase 5).

## 3. Key decisions

| Decision | Choice | Why |
|---|---|---|
| Frontend | React 19 + Vite | Mature Markdown/highlighting/streaming ecosystem; Vite gives fast dev + a static build. Next.js was considered and rejected: its server/client split, caching and router add concepts a local, client-interactive app doesn't use. |
| Styling | Plain CSS + CSS variables, ChatGPT-like aesthetics per [DESIGN.md](DESIGN.md); `lucide-react` icons | A familiar look, measured from chatgpt.com and applied through tokens. Menus and dialogs build on native `<dialog>` and the Popover API. Colours are `light-dark()` tokens following `color-scheme`: the system, or the Light / Dark / System setting (Phase 4). |
| Temporary chat | An ordinary conversation row flagged `temporary` | It reuses every code path, is hidden from the list and search, is deleted when you leave it, and any leftovers are swept at server start. |
| Server | Hono on `@hono/node-server` | Small, Web-standard `Request`/`Response`, built-in `streamSSE` and static serving, trivially testable with `app.request()`. |
| Network | Listens on `127.0.0.1` by default; `HOST` opts into LAN access | There's no auth and the server spends the owner's API key. A non-loopback `HOST` prints a warning. |
| Routing | React Router (declarative mode); URL `/c/:id` from Phase 1 | A reload reopens the same chat. It handles the sidebar + chat layout and later routes like `/projects/:id` without custom routing code. |
| Titles | Generated by the chat model (`OPENAI_MODEL`) after the first answer, in the background | One model setting. The chat isn't blocked while the title is written. |
| Tools | Our own function tools only, no OpenAI-hosted tools | Full control over behaviour, storage and what leaves the machine. Web search uses Brave; project files use local RAG. |
| Tool approval | Per-tool `requiresApproval` flag | Read-only tools run automatically; tools with side effects pause the turn for Approve/Deny in the chat. |
| Attachments | Original kept in `data/files/`; uploaded to the Files API and sent by `file_id` where the endpoint supports it, otherwise sent inline as base64 | Requests stay small on OpenAI, compatible servers without a Files API still work, and the local copy is the source of truth: a file the provider no longer has gets re-uploaded. |
| Providers | One Responses-API endpoint for chat, set by `OPENAI_BASE_URL` / `OPENAI_API_KEY` / `OPENAI_MODEL` | The SDK's own env names, and the same code path for OpenAI, Ollama, LM Studio and other Open Responses servers. The key is optional when a base URL is set, since local servers ignore it. |
| Feature endpoints | Transcription, images and embeddings each have an optional endpoint override, inheriting the chat endpoint | Lets chat run locally while, say, images use OpenAI. With a compatible endpoint and no model configured, the feature is off with a clear message. |
| Server runtime | Node ≥ 26 running `.ts` directly | No server build step. Requires `erasableSyntaxOnly` (no `enum`, no constructor parameter properties). |
| Conversation state | **Stateless**: `store: false`; full history kept in local SQLite and sent on every request | The app owns its data, so nothing depends on OpenAI-side retention, and editing, versions and export are local operations. |
| History shape | **Tree** of items (`parent_id`) | Supports ChatGPT-style message versions. Chosen from Phase 1 so no migration is needed later. |
| Storage | `node:sqlite` (built-in) | Zero dependencies, synchronous, transactional, recursive CTEs for tree paths, FTS5 for search. |
| Streaming call | `responses.create({ stream: true })`, not `responses.stream()` | `stream()` adds an accumulator and `finalResponse()`, but `finalResponse()` rejects on abort (chibot saves partial answers itself anyway) and the accumulator rejects streams from some compatible servers (tested: Ollama `gpt-oss` fails with "missing content at index 0"; `gemma4` and OpenAI pass). Persisting before relaying `response.completed` needs the raw events anyway. |
| Validation | zod schemas in `src/shared` (`@hono/zod-validator` on routes) | One definition per rule; types are inferred from them, and the web imports types only (no zod in the bundle). |
| Wire protocol | Server relays the SDK's own `ResponseStreamEvent`s over SSE | The browser reuses the SDK's types (type-only import), so there are no hand-written mirror types. |
| SSE parsing in browser | `eventsource-parser` | `EventSource` can't `POST`. |
| Markdown | `react-markdown` + `remark-gfm` + `rehype-highlight` + `remark-math`/`rehype-katex` | Standard, safe by default (no raw HTML). Math rendering matches ChatGPT, since models often answer in LaTeX. |
| Testing | vitest units throughout; Playwright e2e from Phase 3 | The UI has little logic worth unit-testing; e2e specs against a fake OpenAI-compatible server (`tests/e2e/fake-openai.ts`) cover the integration and UI regressions. |

### Stateless details

- Requests use `store: false` and `include: ['reasoning.encrypted_content']` so
  reasoning items can be replayed on later turns without server-side storage.
- Each stored item **is** a `ResponseInputItem` (JSON). User turns are stored as
  `EasyInputMessage`; assistant output items (`message`, `reasoning`,
  tool calls, …) come verbatim from `response.completed` → `response.output`.
- The input for a turn is the path from the root to the conversation's
  current leaf, plus the new user message.
- When a request is **stopped**, the partial assistant text is stored as an
  `EasyInputMessage` with `role: 'assistant'`, which is valid input and needs no
  server-side id. A **browser disconnect** (tab closed, network drop) is
  handled the same way: the request's `AbortSignal` aborts the upstream call
  and the partial answer is saved. Nothing generates in the background.
- When a request **fails**, the user message is kept and the UI offers *Retry*
  (that's a regenerate from that message).
- **Context growth:** long chats will eventually exceed the context window.
  The SDK marks `truncation` as deprecated in favour of
  `context_management: [{ type: 'compaction', compact_threshold }]`, which was
  verified with `store: false`: the response carries compaction items, and a
  follow-up sending only the compaction item and what came after it still
  recalls the dropped history (Phase 4).
- **Compatible providers** may not support every request option above
  (`store`, `include`, `context_management`). Phase 1 verifies chat against a
  local Ollama with `gemma4:cloud`. An option a provider rejects gets a per-endpoint switch, added
  only once a real provider needs it.

### Message versions

- **Edit** a user message: a new user item with the same parent as the
  original, so the two are siblings, then a new answer is generated under it.
- **Regenerate** an answer: a new output chain under the same user item.
- Versions of a message are its siblings, ordered by `id`. Switching to a
  version moves the conversation's current leaf to the newest leaf below that
  sibling, so each version keeps its own follow-up history.
- A response that yields several output items (reasoning, message, tool
  calls) stores them as a chain, each the parent of the next. The response's
  `usage` is saved on its last item.

## 4. Architecture

```
Browser (React + Vite)                        Node server (Hono)
┌──────────────────────────┐   HTTP + SSE   ┌──────────────────────────────────────┐
│ App / Sidebar / ChatView │ ─────────────▶ │ createApp(deps)          routes      │
│ Composer / Markdown      │ ◀───────────── │ ChatService     builds request,      │
│ useChat (stream client)  │                │                 streams, tool loop   │
└──────────────────────────┘                │ ConversationStore  node:sqlite tree  │
                                            │ ToolRegistry + Tool (Phase 6/7)      │
                                            │ Config          env → typed settings │
                                            └──────────────┬───────────────────────┘
                                                           ▼
                                   OpenAI or compatible Responses API
```

- **Config:** reads `.env` with `process.loadEnvFile`, validates it and exposes
  typed settings, including one `Endpoint` (base URL, key, model) per
  feature. `main.ts` builds an `OpenAI` client for each distinct endpoint. The
  SDK client already is the provider abstraction, so there's no `Provider`
  class.
- **ConversationStore:** CRUD over conversations and their item tree, path and
  sibling queries, all in SQLite.
- **ChatService:** turns (path + new input + settings) into a
  `responses.create({ stream: true })` call. It yields the SDK events and
  persists the outcome. Later phases add the function-calling loop here.
- **`createApp(deps)`:** the Hono app. It's a factory so tests can inject fakes.
- **`main.ts`:** wires the real dependencies together and starts the server.

Dependencies go in through constructors, so tests pass a fake `OpenAI` client
whose `responses.create` returns an async generator of events. The Playwright
test instead points the real SDK at a local fake server through the SDK's
built-in `OPENAI_BASE_URL` support.

### Data model (SQLite)

```sql
conversations(id TEXT PK, title TEXT, current_leaf_id INTEGER NULL,
              pinned INTEGER DEFAULT 0, archived_at INTEGER NULL,   -- Phase 2
              temporary INTEGER DEFAULT 0,                         -- Phase 2
              project_id TEXT NULL FK → projects,                  -- Phase 8
              created_at INTEGER, updated_at INTEGER)
items(id INTEGER PK AUTOINCREMENT,
      conversation_id TEXT FK → conversations ON DELETE CASCADE,
      parent_id INTEGER NULL FK → items,  -- NULL for the first message
      data TEXT,                          -- JSON ResponseInputItem
      usage TEXT NULL,                    -- JSON ResponseUsage, last item of a response
      model TEXT NULL,                    -- Phase 4: model that wrote it, set like usage
      created_at INTEGER)
settings(key TEXT PK, value TEXT)     -- Phase 4: JSON values over env defaults
items_fts USING fts5(text, conversation_id UNINDEXED)  -- Phase 2: message text for search
files(id TEXT PK, name TEXT, mime TEXT, path TEXT,     -- Phase 5: local copy under data/files/
      openai_file_id TEXT NULL, created_at INTEGER)
projects(id TEXT PK, name TEXT, instructions TEXT NULL,  -- Phase 8
         model TEXT NULL, reasoning_effort TEXT NULL, created_at INTEGER)
project_files(project_id FK → projects, file_id FK → files)          -- Phase 8
chunks(id INTEGER PK, file_id FK → files, text TEXT)                -- Phase 8
chunk_vectors USING vec0(embedding float[N])  -- sqlite-vec, rowid = chunks.id
memories(id INTEGER PK AUTOINCREMENT, text TEXT, created_at INTEGER)  -- Phase 9
```

Search indexes the plain text of user and assistant messages (no reasoning or
tool payloads), written in the same transaction as the item.

| Method & path | Phase | Purpose |

| `GET /api/conversations?q=&archived=1` | 2 | List (pinned first, newest first), archived view, or search (titles + message text, with snippets) |

## 5. Phases

Each phase is built as small commits, one per step, and ends with tests green,
`pnpm typecheck` clean, docs + CHANGELOG updated, and a release commit that
bumps the minor version. Work stops after each phase for review.

### Phase 0 — Foundations ✅
- Dependencies, `Config` (OpenAI or compatible endpoint), Hono app with
  `GET /api/health`, `main.ts`.
- Vite + React shell served by Vite in dev and by Hono in production.
- `pnpm dev` runs both servers; Vite proxies `/api`.

### Phase 1 — Minimal chatbot ✅
- `ConversationStore` (SQLite item tree) and `ChatService` (streaming,
  stateless).
- Single-conversation UI: message list, composer (Enter to send, Shift+Enter
  for a newline), streamed tokens, **Stop** (aborts the upstream request through
  `AbortSignal`), Markdown with syntax highlighting and LaTeX math.
- The first message creates a conversation and moves to `/c/:id`. A reload
  reopens it, and the production server falls back to `index.html` for
  client routes.
- Readable errors that surface `APIError` status and request id.
- **Done when:** a multi-turn chat streams and remembers earlier turns; Stop
  and closing the tab both keep the partial answer; a reload reopens the chat;
  a bad API key shows a readable error; it works against both OpenAI and
  Ollama (`gemma4:cloud`); unit tests cover the store, the service (fake client) and the
  routes.

### Phase 2 — Conversations ✅
- Sidebar: list, new chat, select, rename, delete.
- Date groups (Today / Yesterday / Previous 7 days / Previous 30 days / Older).
- Pin to top; archive with an archived view to restore from.
- Search over titles and message text (FTS5).
- Temporary chat: a toggle on a new chat; see §3.
- Automatic title after the first exchange from the chat model, in the
  background, using low reasoning effort if the model supports it.
- **Done when:** conversations survive a server restart and can be reopened,
  renamed, pinned, archived/restored, deleted and found by search; a temporary
  chat leaves nothing behind.

### Phase 3 — Edit & versions ✅
- Regenerate an answer, edit a user message, `< 2/3 >` version switching.
- Copy buttons for messages and code blocks.
- Keyboard shortcuts (ChatGPT's core set): new chat, focus the composer, copy
  the last answer, toggle the sidebar, search (⌘/Ctrl+K), Esc to stop, and a
  ⌘/Ctrl+/ overlay that lists them (bound with `tinykeys`).
- Token usage for each answer (input, cached, output, reasoning) and a running
  total for the conversation.
- Playwright smoke test against a fake OpenAI backend, including regressions
  found in review: switching chats mid-answer, and returning to a just-created
  chat via New chat.
- **Done when:** editing and regenerating create versions you can switch
  between, each keeping its own follow-ups, and the e2e test passes.

### Phase 4 — Models & settings ✅
Decisions (agreed after probing OpenAI and Ollama): one global model chosen
in the header, answers labelled with their model; one phase; zod adopted now;
compaction on at 64k tokens; math formatting via a built-in instruction.

- **Settings foundation.** zod (schemas shared in `src/shared`, type-only on
  the web). `openDatabase()` runs migrations for one SQLite connection shared
  by `ConversationStore` and a new `SettingsStore` (`settings` table of JSON
  values, environment as defaults). `GET`/`PATCH /api/settings`, never
  returning secrets.
- **Model picker.** The header's model name opens a popover with a search box
  over the chat endpoint's `models.list()` (unfiltered: the lists mix chat,
  embedding, image and audio models), falling back to a text field when
  listing fails. The choice is the `model` setting and applies to new turns,
  edits and regenerations. Each answer stores and shows the model that wrote
  it, so regenerating after switching works like "Try again with…".
- **Reasoning.** `reasoningEffort` setting: unset sends nothing, otherwise
  the SDK's `none`…`max`. Chat requests ask for `summary: 'auto'`; models that
  reject `reasoning` (400) are retried without it, in one helper shared with
  titles. A collapsible "Thinking…" shows the summary while streaming; saved
  answers get a collapsed "Thoughts" disclosure from the stored reasoning
  items.
- **Custom instructions.** *What should chibot know about you?* and *How should
  chibot respond?*, sent as `instructions` with every chat turn (not titles),
  joined with a built-in line asking for `$…$` / `$$…$$` math.
- **Long chats.** `context_management: [{ type: 'compaction',
  compact_threshold }]` with `compactThreshold` (default 64,000 tokens;
  `null` turns it off). Compaction items are stored like other output; a
  turn's input starts at the last compaction item on its path. Shown only as
  a thin "Earlier messages were summarized" divider. Servers that reject the
  option are retried without it.
- **Export / import.** From a chat's menu: Markdown (current path) or JSON
  (full tree, `{ version: 1, … }`, with versions, usage and models). Import a
  JSON file from Settings → Data: validated, new ids, current version kept,
  arrives unpinned and unarchived.
- **Theme.** Light / Dark / System in Settings → General, remembered in
  `localStorage`. Tokens move to `color-scheme` + `light-dark()` so each colour
  is defined once; code highlighting uses our own tokens (the highlight.js
  theme files are media-query based and can't follow a manual toggle).
- **Settings dialog** (DESIGN.md §4): General (theme), Personalization
  (instructions), Model (reasoning effort, compaction), Data (import, archived
  chats). Opens from a sidebar gear and ⌘/Ctrl+,.
- **Done when:** the model and settings apply to new turns and survive a
  restart; reasoning summaries show live and after reload; a chat past the
  compaction threshold keeps working and recalls early facts; exported JSON
  imports back unchanged; the theme toggle works and is remembered. Unit tests
  cover the server parts; Playwright covers picker, settings, thinking, theme,
  export/import and compaction (the fake server gains summary and compaction
  events).

### Phase 5 — Attachments & voice input
- `Config` moves to the zod schemas adopted in Phase 4 as the per-feature
  endpoint variables arrive (§6).
- Images and PDFs added by paste, drag-drop or picker. The original is saved in
  `data/files/`, then sent as `input_image` / `input_file`: by `file_id` after
  a Files API upload where the endpoint supports it, otherwise inline as
  base64.
- If the provider no longer has a file (404), it's re-uploaded from the local
  copy and the request is retried.
- Deleting a conversation deletes its files locally and at the provider.
- Voice input: a mic button records with `MediaRecorder`, and the recording is
  transcribed through `audio.transcriptions` (`OPENAI_TRANSCRIBE_MODEL`) into
  the composer for review before sending.
- **Done when:** the model can answer questions about an attached image and an
  attached PDF, including after the remote file has been deleted; dictation
  fills the composer.

### Phase 6 — Custom function tools
- Abstract `Tool` class (name, description, JSON-schema parameters,
  `requiresApproval`, `run()`) and a `ToolRegistry` that holds the enabled
  tools. The function-calling loop in `ChatService` streams tool activity to
  the UI.
- Approval flow: a call to a tool with `requiresApproval` pauses the turn and
  shows Approve/Deny. A denial is returned to the model as the tool's output.
- Sample tool: **calculator** (exact arithmetic with `mathjs`, no approval).
  AGENTS.md documents how to add more.
- **Done when:** the model calls the calculator mid-answer and uses its result.
  The approval path is covered by tests with a test-only tool, since no
  shipped tool needs approval yet.

### Phase 7 — Web search & image generation
Both are our own `Tool` subclasses, not OpenAI-hosted tools, with per-chat
toggles in the composer.
- **`web_search`** calls the Brave Search API with `fetch` and returns titles,
  URLs and snippets. The model is instructed to cite sources as Markdown links,
  and the UI lists the sources under the answer. It's disabled when
  `BRAVE_API_KEY` is unset. No approval: it's read-only, though the query goes
  to Brave.
- **`generate_image`** calls `images.generate` (`OPENAI_IMAGE_MODEL`) with
  streamed partial images. Results are saved to `data/files/` and rendered in
  the chat. The model receives a reference, not the image bytes.
- **Done when:** a web-search answer shows clickable sources and a generated
  image renders and persists.

### Phase 8 — Projects
- Group conversations into projects (sidebar section, `/projects/:id`).
- Each project has:
  - **files**, searched through local RAG: text is extracted (`unpdf` for
    PDFs), chunked, embedded with `embeddings.create`
    (`OPENAI_EMBEDDING_MODEL`) and stored in SQLite through `sqlite-vec`.
    A `search_project_files` tool returns the best chunks with their file
    names, and the answer cites them.
  - **instructions**, added to every chat in the project on top of the global
    custom instructions
  - **default model and reasoning effort**, overriding the global settings
- **Done when:** an answer in a project cites content from one of its files and
  follows the project's instructions and model.

### Phase 9 — Memory
- A `memory` tool (a `Tool` subclass, no approval) lets the model save facts
  about you. Saved memories are added to the instructions of every chat
  except temporary ones, and the chat shows a "Memory updated" notice.
- A memory page to view and delete memories, plus a global on/off switch.
- **Done when:** a fact told in one chat is used in a new chat and can be
  deleted from the memory page.

## 6. Configuration

Configuration lives in three layers, split by who changes it and how often:

| Layer | Holds | Where | Changed by |
|---|---|---|---|
| Startup & secrets | API keys, base URLs, `HOST`/`PORT`, data dir | Environment / `.env` | Owner, then restart |
| User preferences | Chat model, custom instructions, reasoning effort, memory on/off, tool toggles | SQLite `settings` table (`SettingsStore`, Phase 4) | Settings dialog, live |
| Browser preferences | Theme, sidebar collapsed | `localStorage` | The UI, per browser |

- **Precedence:** conversation or project override (Phase 8) → user setting →
  environment default.
- **Secrets never leave layer 1:** no keys in SQLite, exports or API
  responses. Settings shows only whether a key is configured.
- **`.env` lookup:** real environment variables win, then `.env` in the current
  folder, then `<repo>/.env`, so `chibot` works from any folder.
- **Validation:** zod from Phase 4 (settings, imports, route bodies). `Config`
  moves to it in Phase 5, when the per-feature endpoint variables arrive.

Environment variables:

| Variable | Default | Purpose |
|---|---|---|
| `OPENAI_BASE_URL` | SDK default (OpenAI) | Chat endpoint; any Responses-API server, e.g. `http://localhost:11434/v1` for Ollama |
| `OPENAI_API_KEY` | — | Required for OpenAI; optional with `OPENAI_BASE_URL` |
| `OPENAI_MODEL` | `gpt-6-astra` | Chat model; required with `OPENAI_BASE_URL` |
| `OPENAI_<FEATURE>_BASE_URL` / `_API_KEY` / `_MODEL` | inherit chat endpoint | Per-feature override, `<FEATURE>` ∈ `TRANSCRIBE` (Phase 5), `IMAGE` (Phase 7), `EMBEDDING` (Phase 8) |
| `OPENAI_TRANSCRIBE_MODEL` | `gpt-transcribe` on OpenAI | Voice input transcription (Phase 5) |
| `OPENAI_IMAGE_MODEL` | `gpt-image-2` on OpenAI | Image generation tool (Phase 7) |
| `OPENAI_EMBEDDING_MODEL` | `text-embedding-3-small` on OpenAI | Project file embeddings (Phase 8) |
| `BRAVE_API_KEY` | — (optional) | Enables the web search tool (Phase 7) |
| `HOST` | `127.0.0.1` | Interface to listen on; `0.0.0.0` exposes it on the LAN with no auth |
| `PORT` | `3000` | API server port |
| `CHIBOT_DATA_DIR` | `<repo>/data` | Holds `chibot.db` (Phase 1) and `files/` (Phase 5). The default is resolved from the package location, not the current directory. |

## 7. Risks & open items

- **Compatible providers vary.** Reasoning items, usage details, `models.list()`
  and the Files API may be missing or differ. The UI degrades gracefully: no
  Thinking view, no token counts, a free-text model field instead of a picker.
- **Model names change.** Models are configured through env, never hard-coded
  in logic. Defaults are checked against `models.list()` when the model picker
  arrives in Phase 4.
- **Stored item ids vs. re-uploaded files:** a re-upload yields a new
  `file_id`, so the stored item is rewritten to it. History items aren't
  immutable for attachments.
- **Stateless + compaction compatibility** gets verified in Phase 4. Compaction
  items become part of the tree like any other output item.
- **Export format** is versioned (`{ version: 1, … }`) so that later phases
  (attachments, tool output) can extend it.
- **`sqlite-vec` is pre-1.0** (0.1.x) and needs `node:sqlite` extension loading
  (`allowExtension`). Both get verified at the start of Phase 8. The fallback
  is storing vectors as BLOBs and ranking in JS.
- **Math delimiters:** `remark-math` renders `$…$` and `$$…$$` only. Phase 4's
  built-in instruction asks models for those delimiters; a model that ignores
  it still shows `\(…\)` as raw LaTeX.
- **Imported encrypted items:** reasoning and compaction items carry content
  only the issuing provider/account can decrypt; an import used with another
  provider may need them dropped.
- **Sidebar size:** the list shows the 200 most recent chats (pinned first)
  and search returns 50 hits. Older chats are reachable through search. Add
  paging or "show more" if that limit is ever hit.
- **Menu placement:** CSS anchor positioning isn't widely supported yet, so
  popover menus are placed from the trigger's bounding rect when opened. Switch
  to `position-area` once it is.
- **Bundle size:** the web bundle is ~860 kB (highlight.js grammars, KaTeX).
  That's acceptable for a local app; code-split if it starts to matter.
- **Citations from our own web search** depend on the model following the
  instructions, since there are no hosted `url_citation` annotations. The UI's
  sources list comes from the tool result, so sources are always shown.
